# Lunar v2 规划

## 背景与目标
- v2 分支用于彻底重构当前陈旧的公农历转换库，逐步替换现有实现。
- 提供高效、易扩展、接口稳定的核心能力，优先保证互转正确性和可测试性。
- API 设计遵循“纯函数 + 轻量对象”原则，确保在 Node.js、浏览器等环境中可重用。

## 核心能力
1. 公历转农历：支持至少 1890-2100 年区间，正确处理闰月、节气边界和跨年。
2. 农历转公历：接受结构化输入（含闰月标记），返回时间戳或 `Date` 对象。
3. 互转一致性：公历→农历→公历需保证 idempotent，误差控制在天级别为 0。
4. 辅助工具：提供格式化、序列化（`toJSON`, `toString`）和校验函数的挂载点。

## 数据结构
- `LunarDate`（值对象）：  
  - `year`: number  
  - `month`: 1-12  
  - `day`: 1-30  
  - `isLeapMonth`: boolean  
  - 预留字段：`solarTerm?: string`, `zodiac?: string`（不在 v2 MVP 中实现）。
- `GregorianDateInput`: 接受 `Date`, `number` (timestamp) 或 `{ year, month, day }`。
- `LunarDateInput`: `[year, month, day, isLeapMonth?]` 或传入对象形式，便于后续扩展。

## 架构设计
- `src/core/table.ts`: 编码每年农历信息（闰月、大小月），可生成或导入预计算数据。
- `src/core/converter.ts`: 实现互转算法，保持与平台无关，不直接依赖 I/O。
- `src/api/index.ts`: 暴露 `toLunar`, `toGregorian`, `parseLunar`, `formatLunar` 等方法。
- `src/types.ts`: 集中定义类型与工厂函数，方便对外暴露及第三方扩展。
- 以纯数据驱动方式封装算法，方便替换数据源或扩展至更大年份范围。
- 输入/输出通过可配置的时区归一化工具处理（默认 `Asia/Shanghai`），避免服务器/客户端之间的本地时间偏差。

## 性能与扩展性
- 预先计算年份表，转换时仅做查表和少量算术，避免每次动态推导。
- 支持懒加载或按需分片的数据表，以便未来扩展至 1600-2200 等更大区间。
- 保持不可变数据结构，方便缓存与多线程（Web Worker）使用。
- 允许注入自定义存储（例如 IndexedDB 缓存）但默认使用内存常量。

## 测试与验证
- 构建黄金用例：覆盖闰月首日/末日、节气、年末年初等边界。
- Round-trip 测试：所有黄金样本必须通过公→农→公、农→公→农的往返一致性。
- 属性测试：随机采样日历范围内数据，确保转换结果落在有效区间。
- 性能基线：提供简单 benchmark（如 10 万次互转 < N ms）确保回归可监控。

## 用户期待的必备能力
- 简单易用的 API：通过 `lunar(date)`、`toGregorian(lunarDate)` 等函数即可完成互转，支持 `Date`、时间戳、对象等多种输入。
- 格式化与序列化：提供标准文案（“农历甲辰年正月初一”）以及结构化 JSON 输出，方便 UI 展示或服务端持久化。
- 额外信息挂载点：生肖、天干地支、节气、传统节日等扩展字段需要方便接入，即使首版只暴露占位数据。
- 版本化与类型支持：在 TypeScript / JS 中都有良好类型提示，避免魔法数字。
- 稳定的年份范围与更新承诺：明确支持起止年份以及未来扩展策略，让库使用者可以放心依赖。
- 良好的性能与体积：在浏览器和 Node 环境都能轻量运行，避免大体积表格阻塞主线程。

## 当前难以解决或暂缓处理的挑战
- 历史农历差异：清朝及以前地区在闰月安排和节气算法上有差异，短期内不覆盖 1890 年以前的复杂规则。
- 地区差异与民俗节日：不同地区对节日计算、闰月命名存在不同约定，暂不引入复杂的本地化定制。
- 高精度天文节气：真太阳时、地方经纬度微调需要天文算法或外部 ephemeris 数据，暂时只使用标准历法表。
- 未来年份维护成本：2100 年以后官方历法可能调整，需要官方数据才能更新，暂以保守范围为主。
- 时间区与闰秒问题：UTC 与东八区的转换、闰秒、夏令时等因素的极端情况暂按系统 `Date` 行为处理，不再额外修正。
- 兼容性复杂度：暂不支持农历与其他传统历法（如藏历、回历）的互转，避免引入额外依赖与误用。
